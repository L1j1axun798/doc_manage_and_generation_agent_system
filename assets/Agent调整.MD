请调整现有项目中“四措两案 Agent V1.0”的前端界面。此次任务以界面重构和交互优化为主，不得破坏现有业务流程、会话机制、Agent 调用逻辑及已有功能。

## 一、总体目标

将系统主页面改造为以 AI 对话为核心的工作台，整体交互方式可参考 ChatGPT、DeepSeek 等主流 AI 对话产品，但不得直接复制其品牌元素、Logo、文案或具体样式。

页面应突出以下核心结构：

1. 左侧为会话列表或现有导航区域；
2. 中间为当前会话的消息展示区域；
3. 页面底部固定或半固定显示消息输入框；
4. 用户通过一个会话完成模板选择、人员选择、资料提交、内容生成和后续修改。
5. 不要重构当前已有的Agent模块功能，这些功能应仍实现于后续的每个对话内部。

界面应保持简洁、专业、清晰，适用于风电检测技术服务公司的内部办公场景。

## 二、聊天输入区域改造

聊天输入框是页面的核心操作区域，除普通文字输入和发送功能外，还必须增加以下两个功能入口。

### 1. 添加或选择甲方模板

在聊天输入区域附近增加“选择甲方模板”或“添加甲方模板”入口，支持：

* 从系统已有模板中选择；
* 上传或新增甲方提供的模板；
* 显示当前会话已选择的模板名称；
* 支持在正式生成前更换或移除模板；
* 未选择模板时，应有明确提示；
* 模板选择结果必须绑定到当前会话。
* 上传的新模板，同步放到“资料中心”的“入场前置资料”的对应项目里

该模板代表本次“四措两案”文档生成所依据的目标文档结构和格式。

必须遵守以下规则：

* Agent 生成内容时必须严格基于所选模板；
* 不得擅自增加、删除、合并或调整模板中的章节；
* 不得改变模板原有的标题层级、段落顺序、表格结构、页眉页脚、字体、字号、行距、缩进、编号规则和其他版式；
* Agent 只能在模板允许填写或替换的位置补充业务内容；
* 模板格式保护属于强约束，而不是普通提示；
* 前端需要明确展示“本次生成将严格使用当前模板”的状态信息。

当前任务主要完成前端界面、交互流程和数据结构预留。如果后端暂未实现模板上传或解析接口，应通过独立的 service/API 层封装，并使用清晰的占位数据或 mock 数据，不要将临时数据直接写死在页面组件中。

### 2. 一键选择人员

在聊天输入区域附近增加“选择人员”入口。

功能要求：

* 点击后打开人员选择弹窗、抽屉或下拉面板；
* 支持搜索人员；
* 支持单选或多选；
* 显示已选择人员；
* 支持取消选择和重新选择；
* 人员选择结果必须绑定到当前会话；
* 用户选择人员后，不要求用户再次手动输入人员资料；
* 系统应自动整理所选人员信息，并在调用 Agent 时作为结构化上下文传入。

人员信息后续由我嵌入系统，因此当前实现需要：

* 设计清晰、可扩展的人员数据结构；
* 将人员数据访问封装为独立接口或 service；
* 页面暂时可以使用 mock 数据；
* 不得将具体人员姓名、证件、资质等业务数据硬编码到组件逻辑中；
* 为后续接入真实人员数据库预留明确接口。

建议的人员数据结构至少包含：

* id；
* 姓名；
* 岗位或工种；
* 所属部门；
* 联系方式；
* 证书或资质信息；
* 证书有效期；
* 其他可供 Agent 使用的人员信息。

实际字段应优先兼容项目当前已有的数据模型。

## 三、会话级状态要求

模板、所选人员、聊天消息、上传资料和 Agent 生成结果都必须归属于当前会话。

需要保证：

* 切换会话时，正确恢复该会话之前选择的模板；
* 切换会话时，正确恢复该会话之前选择的人员；
* 不同会话之间的数据不得相互污染；
* 新建会话时，不默认继承其他会话的模板和人员，除非系统现有逻辑明确要求继承；
* 刷新页面后，应按照系统当前已有的持久化机制恢复会话状态；
* 不得为了完成本次界面调整而重写或破坏现有会话模型。

“每个会话内的现有情况保持不变”具体指：现有会话中的消息、任务状态、生成记录、业务数据和操作逻辑应继续正常工作。本次改造只是在现有能力上增加模板选择、人员选择和聊天式操作入口。

## 四、页面交互要求

页面应包含以下状态反馈：

* 当前选中的模板；
* 当前选中的人员数量及人员名称；
* 文件上传状态；
* 消息发送状态；
* Agent 正在分析、生成、修改或完成的状态；
* 接口调用失败时的错误提示；
* 未选择模板时的阻止或警告提示；
* 生成过程中防止重复提交；
* 支持取消不必要的弹窗或选择操作。

模板和人员应以标签、卡片或附件形式展示在输入框上方或内部扩展区域，避免占用过多页面空间。

输入区域建议支持：

* 多行文本输入；
* Enter 发送；
* Shift + Enter 换行；
* 发送按钮；
* 上传文件入口；
* 选择模板入口；
* 选择人员入口；
* 当前上下文状态展示。

## 五、视觉设计要求

整体视觉风格应参考现代 AI 对话产品，但需要符合企业内部系统的专业定位。

重点优化：

* 按钮样式；
* 输入框边框；
* 卡片边框；
* 页面留白；
* 字体和字号；
* 信息层级；
* hover、active、disabled 和 loading 状态；
* 弹窗、抽屉和下拉面板的一致性；
* 会话列表与主聊天区域的层级关系；
* 长文本和长文件名的截断处理；
* 不同屏幕尺寸下的基本适配。

避免：

* 大面积高饱和颜色；
* 过多边框；
* 过度圆角；
* 花哨动画；
* 与现有系统不一致的颜色体系；
* 为追求视觉效果而降低信息密度。

优先复用项目现有的组件库、颜色变量、字体规范和布局系统，不要无必要地引入新的 UI 框架。

## 六、技术实现约束

1. 修改前先分析现有项目结构、路由、组件、状态管理、会话模型和 Agent 调用链路。
2. 优先复用现有组件和接口，不要重复实现已有功能。
3. 不得删除或绕过现有权限控制。
4. 不得改变现有后端接口语义，除非确有必要。
5. 如需新增接口字段，应保证向后兼容。
6. 模板选择和人员选择应分别封装为独立组件。
7. 会话上下文状态应放入项目现有状态管理方案中，不要散落在多个页面组件中。
8. 不要将模板、人员或会话数据长期存储在组件局部变量中。
9. 不要大规模重构与本次需求无关的代码。
10. 保持现有代码风格、命名规范和目录结构。
11. 新增代码应包含必要的类型定义、异常处理和空状态处理。
12. 不得仅制作静态页面，核心交互必须能够运行。

## 七、建议组件拆分

可根据现有项目结构调整，建议至少拆分为：

* ChatLayout：聊天页总体布局；
* ConversationSidebar：会话列表；
* MessageList：消息展示区域；
* ChatComposer：聊天输入区域；
* TemplateSelector：模板选择；
* PersonnelSelector：人员选择；
* ContextAttachmentBar：当前模板和人员状态展示；
* AgentStatusIndicator：Agent 执行状态展示。

不要为了形式强制拆分；如果项目已有同类组件，应优先复用和扩展。

## 八、Agent 请求数据结构

调用 Agent 时，应将用户输入、模板信息和人员信息组合为结构化数据，而不是简单拼接成一段不可维护的字符串。

前端不得把模板完整内容和人员敏感信息直接拼接在 URL 查询参数中。

## 九、执行步骤

请按照以下顺序执行：

1. 阅读并分析现有项目代码；
2. 找到当前主页面、会话页面、输入框组件、状态管理和 Agent 请求入口；
3. 说明准备修改的文件和实现思路；
4. 在不破坏现有功能的前提下完成页面改造；
5. 接入模板选择和人员选择的前端状态；
6. 将模板、人员状态绑定到会话；
7. 调整 Agent 请求参数；
8. 补充 loading、空状态、错误状态和禁用状态；
9. 运行项目现有的格式化、类型检查、构建和测试命令；
10. 修复由本次改动引入的问题；
11. 最后汇总修改内容、涉及文件、接口变化和仍需后续接入的部分。

## 十、验收标准

完成后应满足：

* 主页面以聊天交互为核心；
* 页面视觉结构接近现代 AI 对话产品；
* 可以正常发送文字消息；
* 可以选择或添加甲方模板；
* 可以选择一个或多个人员；
* 当前模板和人员状态清晰可见；
* 模板和人员信息能够随 Agent 请求提交；
* 模板格式锁定约束在数据和提示层面均有体现；
* 模板、人员和消息状态均按会话隔离；
* 切换会话后状态正确恢复；
* 现有会话、权限、Agent 和业务功能未被破坏；
* 页面不是仅有静态样式，而是具备完整交互；
* 项目能够正常启动和构建；
* 不存在明显控制台报错；
* 不引入与需求无关的大规模重构。

请先检查代码并制定具体修改方案，然后直接实施。不要只输出设计建议或伪代码。
